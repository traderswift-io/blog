What goes on a review worksheet?

A table to copy and fill in for each operation you review, with the tests to run against it.

TraderSwift guide2 min readRead Markdown ↗

Copy this into a review document and fill it in for one operation at a time.

FieldWhat to record
OperationExact action, caller, recipient and acceptance boundary
Asset and claimWhat is protected, from whom, and for how long
Attacker accessNetwork, database, host, administrator, signer or physical access
Scheme and versionComplete construction, parameters, library version and profile
IdentityEnrollment, certificate or pin; rotation and revocation rules
Key custodyGeneration, holders, copies, backups, recovery and deletion
EncodingExact authenticated bytes and parsing rules
StateNonces, signing nonces, counters, request IDs and epochs
ThresholdEvery sufficient set of authorities, including recovery
Failure behaviorRejection boundary and whether partial output escapes
EvidenceCommit, configuration, command, input and observed output
StatusDemonstrated, contradicted, untested or outside scope
Next actionSpecific change or test, with an owner

For a negative test, describe what must fail.

Examples include:

  • a wrong identity;
  • repeated participant;
  • malformed group element;
  • altered associated data;
  • replayed request;
  • an injected CRT error.

For an operational test, include at least one state transition:

  • restart;
  • recovery;
  • rotation;
  • revocation;
  • concurrent processing.

These transitions often expose assumptions that normal-operation tests leave untouched.

Keep the strength of the conclusion proportional to the evidence.

A passing test supports the tested behavior in that configuration. A proof supports a model under stated assumptions.

Neither automatically describes:

  • a different build;
  • hidden backup;
  • changed policy;
  • live deployment.
